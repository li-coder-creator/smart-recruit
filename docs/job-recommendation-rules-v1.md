# 求职者岗位推荐：五维规则 V1

创建日期：2026-10-24；规则修订日期：2026-10-25。2026-11-01已完成输入保存、确定性计算和推荐查询接口接入；真实语义模型尚未启用。接口与验收见[契约](job-recommendation-api-contract.md)及[查询阶段报告](job-recommendation-query-stage-2026-11-01.md)。
原型：job-recommendation-preview/index.html（2026-10-24 版本）。
实际开发库证据见 [数据盘点](job-recommendation-data-audit-2026-10-24.md)。
以下是 V1 规则方案；2026-10-25 按本次确认将学历改为100/0，技能改为名称匹配＋别名匹配＋语义匹配，替代原型对应规则。
初始权重和经验扣分系数仍来自原型启发式，不是通过效果实验学习的最优参数。语义评分映射及阈值需要独立校准，尚未定值。

## 1. 业务资格与请求边界

- 当前用户必须为求职者，resumeId 必须属于当前用户。
- 岗位必须为 JobStatus.ACTIVE，企业必须为 CompanyStatus.APPROVED。
- 意向方向使用明确代码映射；未知类别不硬猜为后端或前端。
- strictCity=true 时必须提供可识别城市并先过滤；false 时城市仅参与评分。
- 岗位方向、可选城市过滤后，学历 / 经验 / 技能不足只影响评分和提示，不直接隐藏岗位。
- 本次覆盖偏好只作用于查询，不更新简历；缺失默认项不使用原型示例值填充。
- 2026-11-01确认：默认排除当前用户已投递及deadline早于asOfDate的岗位，提供excludeApplied/excludeExpired独立开关；截止当天及NULL保留。它们不属于五维分数，关闭开关仍不能放宽ACTIVE/APPROVED准入。
- 分数是偏好匹配排序，不是录用概率、资格认证或投递许可。

| 维度 | 输入 | 标准化与评分 | 空值边界 |

| 薪资 | 本次 / 简历期望上限；岗位薪资区间、单位、面议 | 月薪区间中点 / 期望月薪上限 ×100，最高100 | 缺失 / 错误数据 UNKNOWN；明确面议、DAY/YEAR 为 NOT_APPLICABLE |
| 城市 | 本次 / 简历期望城市；岗位城市 | 规范城市一致100，不同0 | 任一侧缺失或不能识别为 UNKNOWN |

## 3. 权重、状态与缺失值（优先规则）

### 3.1 三套初始权重

| 预设 | 技能 | 薪资 | 城市 | 经验 | 学历 |
| --- | ---: | ---: | ---: | ---: | ---: |
| BALANCED | 35 | 25 | 20 | 10 | 10 |
| SALARY_FIRST | 15 | 70 | 5 | 5 | 5 |
| CITY_FIRST | 20 | 10 | 60 | 5 | 5 |

自定义五项为0～100的整数，总和必须大于0。服务端以各项 / 总和归一化；前端滑块只是交互。
负数、未知维度、非整数、超过100或全零属于请求错误，不静默截断。
预设与自定义二选一；均未提供时 BALANCED。状态、规则版本、标准化版本由服务端决定。

### 3.2 三种维度状态

| 状态 | 含义 | score | 是否保留分母权重 |
| --- | --- | --- | --- |
| SCORED | 有证据可计算，包括明确不满足的0分 | 0～100 | 保留 |
| UNKNOWN | 未填写、不能识别、日期 / 数值矛盾、缺少必要确认 | null | 保留；暂贡献0，提示补充 |
| NOT_APPLICABLE | 已明确本次不可比较，例如日薪对月薪、面议 | null | 排除，其它维度按比例归一化 |

权重为0表示用户本次忽略该维度，不伪造其score或参与覆盖率。
字段为空、SQL NULL、空白串均不是“明确不限”。UNKNOWN 不能因重新归一化而变相得满分。
只有 NOT_APPLICABLE 重分配权重；这是针对真实缺失数据对原型的必要补充。

令请求相对权重为 w_i，分母 D=所有非 NOT_APPLICABLE 维度的权重之和：

```text
有效权重比例 = w_i / D
单项贡献 = SCORED ? score_i × w_i / D : 0
总分 = 单项贡献之和
dataCoverage = SCORED维度的权重之和 / D ×100
excludedWeight = NOT_APPLICABLE维度权重 / 请求全部权重 ×100
```

特殊情况：

- D=0：总分null、dataCoverage=0，原因 NO_COMPARABLE_DIMENSIONS，禁止除零。
- 没有正权重的 SCORED 项：总分null；与有证据算出的0分区分。
- 技能权重>0且技能 UNKNOWN：总分null，原因 CORE_SKILLS_UNKNOWN；仍返回其它分项和补全提示。
  避免目前开发库六份空技能简历只靠城市或学历生成看似完整的推荐分。
- 技能权重=0允许其它正权重维度评分；返回实际覆盖率及用户本次已忽略技能的事实。
- 总分null的岗位可以返回并按null置末，不能冒充0分或当作权限错误。

内部使用 BigDecimal 和高精度权重比例，最后总分保留2位 HALF_UP。
排序使用未舍入分数；显示权重不是计算输入，不将显示取整误差再次累加。
有效权重可展示6位、贡献4位；总分始终由高精度原值计算。
同分按 publishedAt DESC（null置末）、id DESC 稳定排序；全局评分后分页。

## 4. 经验规则（优先规则）

### 4.1 岗位要求解析

先 strip，统一 '-'、'–'、'—'、全角数字及内部空格；只接受明确模式，不提取任意文本中的第一个数字。

| 文本 | 标准类型 | 最低月数 | 规则 |
| --- | --- | ---: | --- |
| 经验不限 / 不限 / 无经验要求 / 无需经验 / 0年 | ANY | 0 | score=100，无需证明零年限 |
| 在校生 | STUDENT | 不适用 | 明确求职阶段STUDENT为100，其它已知阶段0，未知阶段UNKNOWN |
| 应届生 / 应届毕业生 | NEW_GRAD | 不适用 | 明确求职阶段NEW_GRAD为100，其它已知阶段0，未知阶段UNKNOWN |
| 1-3（实际旧值） / 1–3年 / 1-3年 | MIN_MONTHS | 12 | 上限保留作说明，不因经验超过3年扣分 |
| 3–5年 / 3-5年 | MIN_MONTHS | 36 | 同上 |
| 5年以上 | MIN_MONTHS | 60 | 达到60个月视为达到下限 |
| N年 / N年以上 / N-M年 | MIN_MONTHS | 12×N | 正整数、范围有序；异常值UNKNOWN |
| NULL、空白、相关经验优先等不能精确解析文本 | UNKNOWN | null | 不能自动当成不限 |

应届 / 在校是求职阶段，不是“年限=0”。不根据年龄、毕业年份或没有经历推断应届身份。
未来遇到“1年以内”等上限型要求，应另补规则，当前标 UNKNOWN，不误用最低年限模型。

### 4.2 候选人正式工作月数

本维度明确为“正式工作经验”，实习、项目经历、课程实践不累计为正式年限。
现表缺少经历类型、是否至今和零经验确认，不能直接把所有记录相加。

确定性算法：

1. 仅选明确标记为正式工作的经历；实习排除。类型未知、可能影响结论时返回 UNKNOWN。
2. startDate 必须存在且不晚于 asOfDate。
3. 明确 isCurrent=true 时截止取 asOfDate，endDate 不得同时填值；false 必须有合法 endDate。
4. 无 endDate 但没有明确至今标记时为 UNKNOWN；periodText“至今”只作人工核对线索，不自动写回或代替标记。
5. 正式工作结束日期不能晚于 asOfDate；倒置区间为 UNKNOWN，不返回负年限。
6. 日期按填写的结束日包含该日，转为 [startDate,endDate+1天) 半开区间。
7. 按开始日期排序，合并重叠及首尾相接区间后，再按每个区间的完整自然月计算并求和。
8. 完整月采用 ChronoUnit.MONTHS.between(start,endExclusive)，不足一个完整月不进位；不同断续区间的零散天数不拼凑月份。

不能直接相加多份同时发生的工作。输出同时保留确认的月数、asOfDate、是否含未知经历及警告。
只要存在可能改变正式月数的未确认记录，actualFormalMonths 为null，不能把部分已知时长冒充完整履历。

零年限：

- 用户明确确认 NONE，且没有正式工作或未分类的矛盾记录：known 0个月。
- 无经历、仅有实习而未确认无正式工作：UNKNOWN。
- 有有效正式工作记录但合并后不足完整月：可计算为0个月，说明“已填经历不足一个完整月”。
- NONE 与正式工作记录冲突：UNKNOWN，提示修正。

### 4.3 年限分数

```text
gapMonths = max(0, requiredMonths - actualFormalMonths)
experienceScore = max(0, 100 - gapMonths × 45 / 12)
```

达到最低月数为100；少12个月为55，少24个月为10，进一步不足最低归零。
45为原型初始启发式参数，建议命名 EXPERIENCE_GAP_PENALTY_PER_YEAR，并纳入规则版本。
不以该分数自动拒绝投递，也不宣称它已验证招聘效果。

## 5. 学历规则（优先规则）

### 5.1 精确别名与等级

| 等级代码 | 接受的明确别名示例 |
| --- | --- |
| ASSOCIATE | 大专、专科、Associate |
| BACHELOR | 本科、学士、Bachelor、Bachelor's |
| MASTER | 硕士、硕士研究生、Master、Master's |
| DOCTOR | 博士、博士研究生、Doctor、PhD、Ph.D. |

英文不区分大小写、统一首尾空白；不按 Java enum.ordinal 或中文字符串字典序比较。
等级顺序使用明确业务rank：ASSOCIATE < BACHELOR < MASTER < DOCTOR。
岗位明确“不限 / 学历不限”为 ANY；其它未识别文本保留 UNKNOWN，不能自动降为大专。
“本科及以上”等明确表达可识别为最低本科；“已取得本科”“必须毕业”等额外毕业约束不吞掉，现数据不能证明时UNKNOWN。

### 5.2 最高学历与在读

V1评分的是“申报学历背景（包含已开始的在读教育）”，不是“已取得最高毕业证 / 学位证”。

- 选择已开始、学历可识别记录中的最高等级，不取最后插入记录、最近结束日期或第一条教育经历。
- startDate 晚于 asOfDate 的计划教育不参与；空开始日期、日期倒置或等级无法识别保留警告。
- 结束日期晚于 asOfDate：标注“在读（按填写日期）”；已结束：标注“填写日期已结束”。均不宣称证书已核验。
- 结束日期为空时不能确认毕业状态；若开始日期有效且等级明确，可作为已开始的申报背景，标记阶段未知。
- 没有可用记录为UNKNOWN，不默认大专或本科。
- 有未识别 / 时间未确认的高阶可能记录时，若已知学历达标可按已知证据给100；若已知学历不足且未知记录可能改变结果，返回UNKNOWN，不直接给不足档。
- 后续若业务要求“已取得学历”，需另增明确申报状态；不得从结束日期到期自动认证毕业。

### 5.3 分数与达标标记

- 岗位ANY：score=100、meetsRequirement=true；不要求候选人先填写学历。
- 可确认申报学历达到岗位最低要求：100、meetsRequirement=true。
- 可确认低于要求：0、meetsRequirement=false，附学历要求高于申报背景的提示。
- 任一必要条件UNKNOWN：score=null、meetsRequirement=null，不冒充明确不满足的0分。

学历采用二值规则：EDUCATION_REQUIREMENT_MET_SCORE=100、EDUCATION_REQUIREMENT_NOT_MET_SCORE=0。
学历权重仍保留；默认10%权重下，达标贡献10分，不达标贡献0分，不重新分配这10%。
分数与 meetsRequirement 分开；学历不达标仍可由其它维度获得总分，不直接过滤岗位或限制投递。

## 6. 技能、薪资与城市细则

### 6.1 技能：名称匹配＋别名匹配＋语义匹配

#### 输入与能力范围

- 技术技能、文档编写、跨部门沟通等通用能力均允许参与；不再把通用能力仅限于展示。
- 简历与岗位均保留输入原文，建议支持一条能力一条记录；名称、掌握程度、补充说明可分别表达，不要求预先枚举全部技能。
- “熟悉Java”可提取为名称Java、程度熟悉；“按规范编写过程文件”可保留完整描述参与语义比较。提取结果必须保留对应原文，无法确定则提示用户确认。
- 已有技能文本和历史岗位字符串继续兼容；明确枚举列表支持逗号、中文逗号、顿号、分号、换行，但自然语言句子中的逗号不能一律当作独立要求边界。
- Spring Boot 不按空格拆开，C++ / C# 不拆符号；复合句拆分必须保留否定和程度的作用范围。无法可靠拆分的必备要求为UNKNOWN，不静默漏掉难处理部分。
- 本维度只计算明确必备能力。preferred_skills仍只提示，不加入分母；重复或已确认同义的必备项合并，避免重复计分。

#### 逐级匹配与约束

对每条岗位要求，依次执行下面流程；前一层已作可靠判断时，不让后一层覆盖结果：

1. **约束检查**：识别否定、掌握程度、版本、范围等明确约束。“不会Java”不能命中“会Java”；“团队内部协作”不能直接等同“跨部门沟通”。矛盾描述或无法确定否定范围时返回UNKNOWN。
2. **名称匹配 NAME**：首尾去空白、大小写等安全规范化后相同，且没有未解决的附加要求，可确定命中100。未知新技能也能按规范化后的相同名称匹配，不依赖完整技能词库。
3. **别名匹配 ALIAS**：用经过维护的等价映射处理SpringBoot→Spring Boot、Vue3→Vue 3等名称。只维护实际需要的别名，不要求收集所有技能。Java≠JavaScript；Vue与Vue 3的兼容关系需要单独声明。
4. **语义匹配 SEMANTIC**：前两层未解决时，使用固定版本的Embedding模型比较完整能力描述，寻找可能对应的简历证据，再结合第1步约束得到匹配判断。语义层也可处理程度或能力范围差异，不能仅凭主题接近给满分。

名称或别名相同只解决“能力名称相同”；若岗位另要求“精通”“独立制定规范”等，不能跳过约束检查直接给100。
明确不同且不兼容的技术名称可直接判0，不得因主题相近由语义层重新判成命中。
明确不具备目标能力可判0；“未独立制定规范”等否定只否定对应要求，不自动否定文档编写等更宽能力。
描述记录的是求职者申报能力；命中不代表系统验证其实际掌握程度。

#### 语义模型、分数和待定参数

- Embedding将文字转成向量，余弦相似度用于寻找语义对应关系；它不是录用概率，也不能直接乘100作为能力匹配分。
- 分离 similarity（模型原始相似度）、matchScore（规则匹配分）、decision（满足 / 部分满足 / 不满足 / 待确认）与evidence（原文证据）。不能把相似度当作判断可信度。
- 满足对应100，明确不满足对应0；部分满足可以取0～100之间的分数，但必须由经过人工样例校准、可追溯的映射产生。
- 模型及版本、中文样例适用性、相似度阈值、部分满足分数映射、拒绝判断区间，均须在计算器实现前确定。当前不虚构0.8等阈值或固定“文档80、沟通60”的评分。
- 校准样例须覆盖同义表达、同主题不同能力、否定、掌握程度、能力范围、技术版本和无法判断的描述；区分调参与最终验收样例，人工判断不一致的样例先澄清规则。
- 不确定区间返回UNKNOWN及原因，不强行归零或给满分。模型未配置、不可用、超时同样返回UNKNOWN，标注服务原因，不能提示用户资料缺失。
- 不使用随机向量、固定演示分或临时改用其它模型伪造正常结果；模型更换后重新校准并变更评分版本。

#### 汇总公式与缺失值

令去重后的岗位必备要求为r_1…r_n，简历能力为c_1…c_m：

```text
pairScore(r_i, c_j) = 名称 / 别名确定分，或已校准的语义匹配分
requirementScore_i = 在可确认的候选证据中选最佳匹配分
skillScore = sum(requirementScore_i) / n
```

- 同一条简历证据可支持多项要求，但每项要求必须分别满足其约束；宽泛的“沟通能力”不自动满足所有细分沟通要求。
- 某项已有充分证据满足100时，其它无关或未知描述不影响该项结论；没有满分证据且未知候选可能改变最佳结果时，该项仍为UNKNOWN。
- 简历有完整可比较能力列表且某项明确没有对应能力，记0；整份列表未填写时为UNKNOWN，不能解释为没有技能。
- 所有必备项均可判断才输出技能分；任一必备项UNKNOWN，技能维度score=null，保留逐项已知结果、待确认项和权重。
- 必备项为空或无法形成明确要求时为UNKNOWN；不因n=0给满分或排除技能权重。
- 技能UNKNOWN且权重>0时继续遵守CORE_SKILLS_UNKNOWN，总分null；已知所有项都不匹配才是技能0。
- 当所有项仅采用100/0判断时，公式退化为“命中项数÷必备项数×100”，兼容原名称集合规则。

#### 展示、调用与可追溯性

- 返回每条岗位要求、最佳匹配简历证据、匹配方式NAME/ALIAS/SEMANTIC、判断与分数、未满足条件及待确认原因。
- 保存原始描述；标准名称、提取属性与向量作为派生结果，不能覆盖用户原文。词典、提取规则、模型和评分规则版本须可追溯。
- 计算器通过独立匹配器接口调用模型能力，名称/别名判断不依赖模型服务可用性；语义缓存按文本、模型及预处理版本区分，规则改变时不能复用旧评分。
- 如调用外部模型服务，只传必要能力文本，避免携带姓名、联系方式和整份简历；具体模型、部署、费用与调用批次在实现方案阶段确定。
- 前端建议支持自由输入能力标签及可选程度、说明，保留自然语言输入；推荐结果展示匹配证据与待确认原因。这里只定义交互需求，尚未修改前端。

### 6.2 薪资

- 所有数值按元，期望按元/月；原型15K需由接口按15000元表达，不把15与数据库15000比较。
- 数值须正数、区间有序；期望仅明确上限时可计算，目标上限缺失为UNKNOWN。
- MONTH且数值有效：min(100, ((salaryMin+salaryMax)/2) / expectedSalaryMax ×100)。
- 明确negotiable=true且上下限为空：NOT_APPLICABLE；DAY/YEAR对期望月薪同样NOT_APPLICABLE，第一版不猜工作天数或奖金。
- 面议同时存在数值、单位未知、倒置区间、缺少岗位数值：UNKNOWN，不能当合法面议重分配权重。
- 期望下限用于区间校验及“岗位上限低于期望下限”的提示；本公式分母使用期望上限，不暗换口径。
- 13薪 / 14薪当前无字段，不参与评分，也不生成展示值。

### 6.3 城市

- 使用明确城市代码和别名；实际旧值Shanghai兼容为上海，上海市与上海同码。
- 不能把当前居住城市偷偷当成期望城市，也不将同省城市视为相同城市。
- strictCity=true 且期望城市空 / 无法识别为请求错误；false 时未知城市返回UNKNOWN。
- 城市已知但不同为0分，返回可沟通异地的事实提示，不擅自修改求职意向。

## 9. 下一阶段交付与学习重点

建议顺序：结构化输入兼容迁移草案与技能样例标注 → DTO/VO及逐项证据契约 → 名称/别名匹配器 → 语义模型选型与校准 → 特征构建与五维计算器 → Mapper/Service/Controller → Postman回归。
完整技能验收必须覆盖三层匹配；只完成名称/别名时只能认定该子阶段完成，不能宣称语义匹配已上线。

需能解释：

1. 空数据与明确0分为何不同，日薪不可比较为何能排除权重。
2. 申报学历背景和已取得学历为何不能混用。
3. 工龄为什么先区间合并，再计算月数；实习为何不直接累计。
4. prototype常数为何是初始业务规则，如何通过版本管理保持可追溯。
5. 当前数据不能证明推荐有效性，测试通过也不能推导命中率提升或招聘转化率。
6. 文本向量相似度为什么不等于能力满足，否定、程度和范围如何影响判断。
7. 为什么要返回匹配证据、保留UNKNOWN，并对模型、别名和评分映射分别管理版本。
