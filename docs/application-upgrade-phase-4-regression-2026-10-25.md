## 4. 请求、响应要点与结果

以下为实际断言/数据库核对的响应要点，不是额外执行的示例请求。

| 请求场景 | 实际验证结果 |
| --- | --- |
| 企业新建线上面试 | HTTP 200/业务 200；status=SCHEDULED、version=0；平台/链接/说明去首尾空白 |
| 有未来或进行中有效安排时再次创建 | 业务 500/data=null，不产生第二场有效安排 |
| ONLINE→OFFLINE→ONLINE 完整改约 | 版本 0→1→2；切换后原方式字段清空，省略可选说明会清空 |
| 缺失/负数/旧版本、小数、字符串版本、Long 溢出 | 明确拒绝；不会将小数截断后写入 |
| 过去开始、结束等于开始、时间反转 | 业务拒绝，无安排或事件残留 |
| 平台51、链接超1000、说明501、原因501 | 业务拒绝；合法长度边界 50/1000/500/255 已验证 |
| 线上缺平台/链接、同时填地址；线下缺地址或夹带线上字段 | 业务拒绝 |
| javascript/file/ftp/相对/无host链接 | 业务拒绝；服务端不访问会议 URL |
| 未知枚举/数字枚举、归属/状态/初始版本等未知字段 | 业务拒绝，不能覆盖服务端字段 |
| 未登录 | HTTP 401，不写入 |
| 求职者、外企、未准入企业、管理员读写企业安排 | 业务拒绝；所属企业正常读取 |
| interviewId 不属于路径投递 | 业务拒绝，不修改其它投递场次 |
| 正在进行的场次改约 | 拒绝；未结束时可手动取消 |
| 已取消/过期场次重复取消或改约 | 拒绝；取消后可创建新场次，历史保留 |
| 过期场次读取 | status 仍为 SCHEDULED，timingStatus=EXPIRED，不冒充 COMPLETED |
| 岗位已结束且简历缺失、岗位暂停且跨自然日 | 所属企业仍可安排并读取，公开跳转标记正确 |
| 新/改约/取消时间线 | 三种真实事件；旧/新时间及方式保留，历史完整性标记不被伪造为 true |
| 企业列表/求职者详情/近期面试隐私 | 不返回 createdBy、updatedBy、cancelSource、操作者账号或任意原始 JSON |
| 近期面试本人/他人/空用户 | 只读本人；无安排 interview=null，包装保留 serverTime/timeZone |
| 近期优先级 | 进行中按较早开始返回；开始相同按 ID 升序；排除其它用户和投递终态 |
| 非法未来日历日期、Z/offset后缀、四位小数秒 | 独立 E 组拒绝；结束时间设置得更晚，避免其它校验掩盖解析问题 |

线上/线下字段只在授权安排 VO 展示。事件快照只包含时间、方式和取消原因七个白名单键，
不复制会议 URL、地址和 candidateNote，旧快照没有被后来的改约覆盖。

## 5. 四类失败回滚

安装故障触发器前，对隔离库 job_application、application_interview、application_event 的全部行保存基线。
触发器只作用于隔离库事件插入，测试了：

1. 新安排已经插入，INTERVIEW_SCHEDULED 保存失败。
2. 原安排内容和版本已经更新，INTERVIEW_RESCHEDULED 保存失败。
3. 手动取消状态和版本已更新，INTERVIEW_CANCELLED 保存失败。
4. 投递已更新为录用，第一场取消及事件已执行，在第二场取消事件保存时失败。

四类均响应业务 500。数据库逐行比对确认投递状态、面试证据、安排字段、版本、创建/更新时间、
取消字段和事件全部与基线一致；第四类证明不是仅最后一行回滚，而是整个多表事务回滚。
移除故障后重试均成功。没有要求自增 ID 连续，回滚消耗的自增号不属于业务残留。

终态恢复后，两场未结束安排（包括正在进行）同时取消；已过期和此前取消的场次状态/版本保留。
自动取消的 actorType=SYSTEM，原因是“投递流程已结束，安排失效”。

## 6. 九组并发

隔离库在事件插入处延时 2 秒，使请求持锁区间可观测；每组均通过开始/结束时间断言实际重叠。

| 并发组 | 验证结果 |
| --- | --- |
| 同一投递同时创建两场 | 一成功一拒绝，只有一场有效安排 |
| 同版本同时改约 | 一成功一拒绝，版本只递增一次 |
| 同版本改约与取消 | 一成功一拒绝，不覆盖较新版本 |
| 创建先发、录用随后 | 终态请求成功；若创建成功，随后取消；最终无有效安排 |
| 改约先发、录用随后 | 合法先后处理可都成功；最终取消，版本/事件对应 |
| 手动取消先发、拒绝随后 | 终态成功，取消事实保留，不重复取消 |
| 录用先发、创建随后 | 创建按锁后状态拒绝，最终无有效安排 |
| 录用先发、改约随后 | 改约按锁后状态/版本拒绝，最终已取消 |
| 拒绝先发、手动取消随后 | 不再重复取消，不增加重复版本/事件 |

“排期操作先成功，随后流程结束”是合法顺序，因此终态竞争不要求所有组都只能一个成功。
约束是不能出现重复有效场次、旧版本覆盖或通过接口进入终态后残留有效安排。
本轮是九组双请求验证，不是高并发容量证明。

## 7. 数据库最终核对

面试隔离库：36 条合成投递、30 条安排、48 条事件。核对通过：

- 同一投递没有两场 SCHEDULED 且 end_time>now 的有效安排。
- 本轮通过接口进入终态的投递无有效安排残留。
- 每个场次的 version 与其实际改约/取消事件条数一致。
- 事件 interview_id 与 application_id 归属一致，JSON 只有白名单键。
- 旧历史标记保持 false，无补造 APPLIED。
- 无残留测试触发器，开发库前后数据指纹一致。

特例夹具 1030 故意预置“旧终态却有未结束安排”，只用于验证近期查询排除终态，
没有通过本轮状态更新接口处理它，不将其算入自动联动后的终态残留检查。
该夹具不在开发库，不能据此宣称系统启动时会清理一切旧异常数据。
