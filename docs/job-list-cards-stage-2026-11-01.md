# 普通岗位卡片字段补齐与回归

日期：2026-11-01。

## 交付范围

业务背景：原型“全部岗位”卡片需要展示企业、技能和岗位简介，原 GET /job 返回字段不足。

实现仅涉及 `JobListVO` 与 `JobMapper` 的三个列表投影，新增12个字段；保持接口路径、既有字段、分页形状、排序、权限和搜索范围。企业公开主页和企业管理列表复用同一个 VO，因此同步补齐。

详细类型、空值、薪资及技能展示语义见[字段契约](job-list-card-contract.md)。没有数据库迁移、前端修改或 Git 提交。

Mapper 使用企业主键关联，避免逐岗位读取企业；没有把能力子表的一对多关系加入分页 SQL。Controller 和 Service 保留参数入口、权限校验、分页及批量投递统计的既有职责。

## 回归准备与身份

- 业务请求通过 Postman MCP 执行，用例持久加入 `SmartRecruit API - Optimized Regression / 03 Job / 普通岗位卡片回归 2026-11-01 / A 卡片字段分页与权限`，执行前核对37条持久请求的方法、URL、请求体和脚本一致。
- 隔离端口18092，数据库 `smart_recruit_job_cards_1793524437061`。复制源库表结构，创建合成身份与数据；源库仅用于读取结构及前后数据指纹。
- 合成身份：101、102为求职者，103为企业201所属账号，104为管理员；企业201审核通过，202待审核，203审核拒绝。
- 30个岗位中27个招聘中；企业201有28个岗位，含25个招聘中岗位。1022号岗位有三条能力子记录，验证列表仍一岗一行。时间统一固定，测试排序与跨页结果。

## 已知边界与学习点

字段补齐阶段验收时，普通列表只限制岗位招聘中，未审核企业的在招岗位仍可被查询；原型要求的企业名/技能搜索与薪资排序当时尚未实现。后续查询阶段已完成这些规则，当前行为见[查询契约](job-browse-query-contract.md)。本报告的37条用例与计数记录的是字段阶段的历史快照；当前回归以查询阶段集合为准，历史环境保持关闭。

应能解释：为什么公开列表采用VO明确投影、为什么LEFT JOIN可保留历史关联缺失的岗位、多对一关联为何不会放大分页、能力子表为何不能直接联查分页，以及列表展示文本和推荐匹配证据为何需要区分。
