# 岗位操作记录开发草案

本文件保留原始设计。2026-10-04 用户授权后已完整实现并创建本地记录表，实际状态和待验收项见 job-activities.md。

## 背景、范围与契约

快速原型岗位详情包含操作时间线：保存草稿、发布、更新、暂停、恢复、结束。
现有 OperationLogAspect 只写应用日志，不保存 jobId、操作者和可查询的业务时间线，无法直接支持此页面。
需要建立独立的业务记录，在业务修改成功时同事务写入，不开放前端新增记录接口。

沿用 GET /job/company/{id}/activities?limit=5 和既有 JobActivityVO。
建议默认 5 条、允许 1～20 条，新增独立具名常量，不复用最近投递的业务常量。
返回 id、operation、operationText、operatorName、createTime；无记录返回空数组。
企业角色、岗位存在性、岗位归属检查与招聘进展一致；草稿也可查询记录。
按 create_time DESC, id DESC 排序，不返回总数。

## 数据模型建议

表 job_activity：

| 字段 | 建议类型与约束 | 说明 |
| --- | --- | --- |
| id | BIGINT，主键，自增 | 记录 ID |
| job_id | BIGINT NOT NULL | 岗位 ID |
| operator_user_id | BIGINT NOT NULL | 实际操作者，来自登录身份 |
| operator_name | VARCHAR(100) NOT NULL | 操作者展示名快照，昵称空白则使用用户名 |
| operation | VARCHAR(32) NOT NULL | 与枚举一致的操作编码 |
| create_time | DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) | 实际发生时间 |

新增索引 (job_id, create_time, id)。不重复保存 company_id，查询归属从岗位取得。
记录名字快照，避免以后修改昵称造成旧时间线操作者变化。
建议岗位外键 ON DELETE CASCADE：当前业务只允许物理删除草稿，删除草稿时删除其展示记录。
这是页面业务时间线，不承担草稿删除后仍需永久保留的独立审计职责；若未来需要审计删除行为，应另行定义保留策略。

## 事件生成规则

新增 JobOperation 枚举，编码和文案保持唯一来源：

| 操作编码 | 文案 | 写入时机 |
| --- | --- | --- |
| CREATE_DRAFT | 保存草稿 | 新草稿插入成功 |
| PUBLISH | 发布岗位 | 直接发布或已有草稿发布成功，各写一条 |
| UPDATE | 更新岗位信息 | 内容保存成功，包括编辑草稿 |
| PAUSE | 暂停招聘 | 招聘中变为暂停成功 |
| RESUME | 恢复招聘 | 暂停变为招聘中成功 |
| END | 结束招聘 | 招聘中/暂停变为结束成功 |

读取详情、最近投递、进展不生成业务操作记录。
按现有六类契约，删除草稿不写可供已删除岗位查询的事件。
参数错误、无权限、岗位不存在、状态冲突和重复状态请求失败时均不写记录。
UPDATE 暂定义为“内容保存成功”，不承诺识别字段完全相同的无效编辑；若需要去重，单独定义内容比较规则。

## 实施顺序与依赖

1. 先确认字段、事件规则及删除策略，编写迁移草案，检查目标数据库并备份相关表。
2. 创建 JobOperation、JobActivity 和 JobActivityMapper，沿用 JobActivityVO。
3. 修改 JobMapper.add，加入 @Options(useGeneratedKeys = true, keyProperty = "id")。
   当前 add 返回 void 且未配置主键回填，新增岗位后生成记录需要真实 jobId。
4. 将六类岗位写操作置于事务中：校验 → 修改岗位 → 插入操作记录 → 提交。
   现有部分方法没有事务，需要逐个补充；BusinessException 是 RuntimeException，默认会回滚。
5. 更新 SQL 返回受影响行数；状态变更使用 WHERE id AND 原状态的条件更新。
   只有影响 1 行才写事件，0 行报冲突；仅先查状态再按 ID 修改不能防止并发重复记录。
6. 缓存失效应安排在数据库提交之后，避免事务尚未提交时被旧数据重新填充。
   在加入事务时复查目前“立即删除 + 延迟删除”的位置，不能将固定延迟当作提交保证。
7. 实现活动查询：校验 limit、企业和岗位归属 → 查询记录 → 枚举补齐 operationText。
8. 使用 Postman MCP 保存并执行回归，最后复查事务、权限、事件生成数量和兼容旧数据的行为。

数据库变更失败则记录不能落库；记录写入失败也必须使岗位修改回滚。
事务必须由 Spring 代理调用的公开 Service 方法开启，不能依赖同类内部调用上的事务注解。
业务时间线直接在 Service 记录，通用 AOP 日志继续用于排查请求。

## 旧数据处理

不根据当前岗位状态和 update_time 伪造暂停、恢复、结束或编辑历史。
旧岗位可以暂时没有记录，前端显示“暂无操作记录”，从功能启用后开始积累。
只有能证实事件和真实时间时才单独补录，例如可靠的 published_at；create_time 不一定代表直接发布。

## 验收与交付

- 六类成功操作各增加一条正确事件；直接发布不会多出 CREATE_DRAFT。
- 草稿和已发布岗位都能查记录，顺序和 limit 正确。
- 越权、非法状态和其他失败请求不新增事件。
- 记录插入失败时岗位修改回滚；这项必须核对数据库状态，不能只看接口响应。
- 并发状态请求最多一个成功迁移及对应事件。
- 新建岗位有真实主键回填；操作者来自登录身份。
- 草稿删除不留下孤立展示记录；旧岗位不伪造历史。

## 面试要点

重点理解业务事件与技术日志的区别、同事务原子性、主键回填、条件更新防止并发冲突、
Spring 事务代理及自调用限制、事务提交后的缓存失效，以及历史数据不能凭当前状态推断。
