## 一、确定缺口：前后端联调前优先完成

### P1-1 企业岗位列表三项统计（后续已完成）

原型每行展示投递总数、“新”投递数和当前面试数。
当前 JobListVO 与 JobMapper.findCompanyJob 的 SELECT 均没有这些字段。
单岗位 progress 已能查询这些指标，但逐行调用会让一页产生 N 个额外请求。

建议保持 GET /job/company，使用独立 CompanyJobListVO 增加：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| applicationCount | Long | 本岗位全部状态投递总数 |
| pendingApplicationCount | Long | 本岗位当前待处理投递数，即原型“新” |
| currentInterviewApplicationCount | Long | 本岗位当前面试中的投递数 |

企业统计不应顺带暴露到求职者列表；没有投递返回 0，草稿按既定契约返回三项 0。
无需新增数据库列，也无需保存冗余计数。
“新”明确表示待处理，不是未读，不新增阅读标记和已读接口。

推荐实现顺序：先分页查询本企业岗位 → 提取当前页 ID → 一次 GROUP BY job_id 聚合投递 →
按 jobId 合并三项计数并补零。聚合限定当前页 ID，避免循环查询和整企业全量聚合。
PageHelper 只包住岗位列表查询，先保存分页信息后再调用聚合 Mapper；空页跳过聚合，避免 IN ()。
分页 total 为岗位数，不是投递 JOIN 后的行数。

验收：无投递、各投递状态、多投递、草稿、暂停、结束、关键词、状态筛选、空页、企业隔离；
同一岗位的三项计数与 progress 接口在相同数据状态下相符。
并发变化时两个独立 HTTP 请求可能读取不同快照，不要求跨请求永远数值相同。

### P1-2 缺失简历会让投递详情及完整列表丢记录（后续已完成）

ApplicationMapper.findApplicationDetail、findCompanyApplication、findJobseekerApplication 仍使用 INNER JOIN resume。
最近投递和聚合统计已经不依赖这个关联，导致同一条投递在不同页面的可见性不一致。
本轮隔离测试确认：状态修改成功、最近投递显示该记录，但 GET /application/{id} 报“该投递不存在”。
开发库只读检查发现 1 条实际缺失简历关联的投递。

建议先修复历史可见性：投递作为查询主记录，展示关联按需要 LEFT JOIN；保留 applicationId、jobId、
状态与时间，并明确缺失资料的展示契约。不能伪造简历内容，不能因为 JOIN 结果不存在而误判投递不存在。
Service 的登录身份、企业岗位归属和求职者投递归属检查仍必须保留。
该修复涉及投递查询，与岗位最近投递点击链路相关，不要求重新实现冻结的简历模块。

长期是否保存投递时简历快照、是否允许删除投递中的简历，属于后续明确需求；
当前修复不自动改变简历删除规则，也不自动新增快照表。

验收：简历存在、缺失、资料空白；企业与求职者均能看见原投递；越权仍拒绝；
列表数量与原始投递一致，详情显示资料缺失而不是整条投递不存在。

### P2-1 非法参数的错误提示需要明确

GlobalExceptionHandler 只专门处理 BusinessException 和 MethodArgumentNotValidException。
本轮 status="abc"、不完整 JSON，以及上轮 limit=abc 都被拒绝，但返回通用系统异常文案。
功能上没有放行非法输入，问题是客户端无法获得明确原因。

建议专门处理请求参数类型转换和请求体解析异常，返回稳定的参数错误文案；
与当前 Result 规范一致，不在本任务顺带重构全局 HTTP/业务码协议。
这是共享异常处理的体验修复，不是白名单规则错误。

## 二、需要明确规则后再决定实现

### 截止日期的含义

deadline 当前保存并展示“计划截止日期”；发布和招聘中/暂停岗位编辑时不允许过去日期。
投递入口只检查 ACTIVE，恢复接口只检查 PAUSED；没有到期自动结束或拒绝投递的逻辑。

先决定：它只是计划展示，还是当天结束后限制新增投递？是否到期自动改为 ENDED？
现有契约尚未要求自动结束，因此不能直接定为缺少定时任务。
如果采用展示日期，说明需明确；如果采用业务期限，再设计投递校验、恢复校验、时区及到期处理。
届时还要区分“发布时的新期限校验”和“保留历史期限的内容编辑”，避免所有编辑都因旧日期失败。

### 暂停/结束与投递竞争

ApplicationServiceImpl.apply 普通读取岗位状态后再插入投递。
JobService 的暂停/结束会锁岗位，但新增投递没有参加同一把岗位锁。
所以“求职者已读 ACTIVE，企业随后暂停，求职者之后提交投递”这一时序在代码上没有被排除。
这属于静态确认的并发边界，本轮没有执行它的竞态实验，不将其描述为已经复现的缺陷。

如果要求暂停/结束提交后不接受尚未落库的投递，可以让 apply 也在事务中锁同一岗位行，
锁后读取状态再插入；同时评估锁顺序与同岗位写入串行的成本，并补独立 Postman 并发验收。
若允许已开始提交的投递完成，需要把这个行为写入契约。

## 三、建议项：不必阻塞当前原型联调

1. 查询索引按执行计划评估。现有 (job_id,status,create_time) 不直接覆盖不筛选 status 的最近投递排序；
   可评估 (job_id,create_time,id)。企业 ALL 列表也需核对现有 company/status/update 索引在未筛 status 时的排序。
   不直接加所有索引，不声称性能提升，先用接近实际数据的 EXPLAIN 做依据。
2. 完整收到的投递列表当前为 List，无分页和按岗位/状态筛选。
   若要从岗位跳转到完整收到的简历页面，作为下一模块扩展查询契约；原型当前仅要求有限条最近投递。
3. 并发重复投递已有数据库唯一索引保护，但 DuplicateKeyException 目前落到通用异常提示。
   可将该唯一键冲突翻译为“请勿重复投递同一岗位”，保留其他数据库错误的真实处理。
4. 岗位详情缓存目前是提交后尽力失效；Redis 失败和长时间旧读回填不保证严格一致。
   可靠重试与版本控制可作为后续工程优化，不把本轮功能测试当成缓存故障证明。
5. 新环境启动前执行已有三份迁移，维护迁移顺序与已执行标记；本地已执行，不重复运行。
6. 长文本 DTO 字段目前没有明确业务长度上限，可另定上限并匹配 TEXT 容量；
   不临时拍一个业务数字，也不在当前检查中修改 DTO。

## 四、联调需要遵守的新契约

- 总览和单岗位的“面试人数”均展示 currentInterviewApplicationCount。
- 转化率仍用 interviewApplicationCount（累计进入过面试）/ applicationCount；
  不用当前面试人数反算转化率。历史未知或无投递显示“—”，不替换为 0%。
- 计数单位是投递记录，不按跨岗位的求职者去重。
- 企业处理投递时仅展示当前状态允许的目标，后端仍独立校验。
- 内容保存不能通过 status 变更岗位状态，使用独立发布/暂停/恢复/结束接口。
- 已结束岗位没有重新发布接口；原型对已结束岗位出现“完善并发布”的入口需要在前端按契约调整。
- 原型下拉薪资单位展示中文，请求需映射 MONTH/DAY/YEAR；标签文本拆分由前端展示层处理。
- 所有业务失败检查 code，不能只看 HTTP 200；成功后刷新受影响的列表和统计。
- 推荐人才按用户决定暂缓，本轮不新增推荐接口、评分规则或算法。

## 五、推荐下一个企业式任务

任务：补齐企业岗位分页列表的投递统计。

- 背景：原型岗位行缺少可用的真实统计，逐行调用 progress 会增加请求和数据库查询。
- 范围：仅 GET /job/company 的返回契约、企业 VO、分页后批量统计 Mapper/Service；不改变岗位状态或数据库表。
- 影响模块：JobController、JobService、JobMapper/ApplicationMapper、企业分页 VO、Postman 集合。
- 验收：三项计数准确、没有投递补零、草稿显示契约正确、分页 total 不被 JOIN 放大、无逐行查询、企业隔离。
- 边界：空页、同一用户投递不同岗位、已结束岗位保留历史、筛选和关键词不改变总览的统计范围。
- 交付：接口契约表、企业 VO、批量聚合查询、Service 合并逻辑、持久 Postman 用例与验收结果。

建议学生先给出 VO 和查询设计，再实现，由助手复查；不在本轮测试任务中自动代写。
面试需理解 N+1、先分页再聚合、COUNT 条件聚合、LEFT JOIN 与历史可见性、权限过滤、分页总数和快照边界。
当前阶段可以准确描述“支持岗位生命周期和招聘进展统计，并通过状态迁移回归”；
不要将助手实现的白名单包装为独立完成，也不声称吞吐量、规模或性能提升。
