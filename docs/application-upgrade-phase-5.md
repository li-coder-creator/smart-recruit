## 验收分组

| 分组 | 请求数 | 内容 |
| --- | ---: | --- |
| A | 79 | 六条 API 新投递：逐级录用、跳到面试后未通过、直接录用、直接未通过、有效排期、另一企业/求职者隔离 |
| B | 60 | 7/30 自然日起点、当前时间上限、ALL、默认10条、稳定分页、状态组合、非法参数、空用户和脏状态 |
| C | 51 | 4种岗位状态×4种企业存在/审核情况，岗位缺失、简历缺失/归属变化/空标题、薪资和权限 |

A 组从 POST /application 创建真实新记录，不把预置面试阶段的旧投递充作完整流程证据。
之后通过查询获得 ID，推进状态并创建/改约/取消/重建面试，再读取详情、概览、近期面试和旧接口。
数据库审计要求每条新记录仅有一条 APPLIED，historyRecordedFromStart=true，跳级不补造中间阶段，
version 等于实际改约/取消事件数，终态没有有效排期。

B 组日期起点为 2026-10-22T00:00:00 和 2026-09-29T00:00:00。
等于起点纳入；now 后一秒排除；ALL 只取消下限，仍排除未来。
概览按契约统计全部历史，不跟随列表窗口；故意构造的未来异常投递也参与该总览计数，不隐式改变统计口径。

C 组中 companyAvailable 只表示关联企业存在；jobViewable 才同时要求 ACTIVE 和 APPROVED。
无法正常通过现行写接口产生的历史孤立记录，仅在新隔离库准备夹具时临时关闭会话外键检查，随后立即恢复。
不删除开发资料，不对开发库关闭约束，也不把旧异常数据构造描述成正常业务流程。

## 复现步骤

1. 使用 JDK17/Maven 编译当前后端；准备 target/files-classpath.txt。
2. 用项目依赖编译 ApplicationEventFixture.java、ApplicationAcceptanceClock.java、ApplicationAcceptanceFixture.java 到 target。
3. 设置 APPLICATION_ACCEPTANCE_STATE_FILE 为 target 下全新状态文件，然后执行 application-acceptance-regression.cjs 的 setup。
4. 确认18087空闲后 start，检查启动日志；prepare 将用例持久保存，verify 比对主集合请求、请求体和脚本。
5. 顺序运行 A、B、C；audit 比对数据库不变量和开发库指纹；guard-off 关闭开关。
6. 核对状态文件中 serverPid 的实际命令行/端口，只停止本次测试实例；保留隔离证据和测试库供复查。
7. 用相同的APPLICATION_ACCEPTANCE_STATE_FILE执行application-acceptance-evidence.cjs，生成脱敏统计与数据库证据；正式关闭回归开关后用status核对非敏感运行状态。

首次执行可创建主集合目录及执行副本；后续 setup 复用 manifest 的目录与执行副本 ID，避免重复目录。
每个全新隔离夹具按 A/B/C 顺序运行一次。重复运行有写入的 A 组必须重新准备隔离库，不能把已变更数据当作初始状态。
执行副本仅用于避免运行主集合中其他模块的写入请求；主集合中保留相同的正式回归用例。

## 后端交付边界与面试考点

本轮固定求职者新查询和五个排期接口的契约；旧接口继续保留。
前端企业排期入口、求职者投递卡片/详情/日历以及真实浏览器联调为下一阶段。

后续独立议题包括投递时资料快照、企业投递列表分页、岗位截止时间规则、岗位结束与新增投递的并发协调。
这些议题不能从本期验收通过推导为已经完成。

需掌握：自然日窗口和固定Clock；SQL聚合与分页口径；LEFT JOIN 和可用/可查看标记；
新旧历史完整性；父行锁与版本号的不同作用；真实事件同事务写入；从请求响应到数据库不变量的验收方式。
请求数和断言数表示回归执行结果，不表示吞吐量、业务规模或性能提升。
