# 推荐查询接入、代码拆解与验收（2026-11-01）

## 1. 先列边界与待办

- 确定限制：真实语义模型、掌握程度和范围校准尚未启用，相关条目返回UNKNOWN，不承诺完整语义匹配已经验收。
- 确定差距：原型“全部岗位”Tab复用的GET /job目前返回JobListVO，不包含企业名称、企业ID和技能标签等卡片字段。本轮推荐Item已包含这些字段，普通岗位列表需要在下一阶段单独补齐。三个新增推荐接口通过不等于两个Tab的全部业务均已完成。
- 工程边界：为保证全局排序，本期把SQL资格筛选后的候选加载到内存，再按方向/城市筛选、评分排序分页。能力子表按批读取，避免逐岗位查询；没有针对大规模岗位库做基准测试，不能宣称已有大规模推荐能力。
- 部署边界：验收使用独立服务18091，没有重启用户的8081服务。日常使用需要重启后端加载新接口。

本阶段结论：三个推荐入口、资格过滤、偏好覆盖、可解释结果及全局分页已经实现并通过持久接口回归，可为推荐Tab联调提供后端基础。

## 2. 任务范围与已确认规则

业务目标是“求职者选定本人简历，调整本次偏好，获得真实岗位和可解释匹配分”。原型示例值不能替代缺失的真实偏好。

本次用户确认：默认排除当前用户已投递、以及截止日期已过的岗位，提供两个独立开关。截止当天仍保留，deadline=NULL不视为过期。投递排除不依赖所选简历，不因历史投递已拒绝而重新推荐。

岗位ACTIVE、企业APPROVED两项准入始终生效；方向必须明确，strictCity=true时必须有可识别期望城市。学历、经验、技能不满足只影响分数与提示，不作为隐藏岗位的资格条件。

新增接口：

| 请求 | 用途 | 关键行为 |
| --- | --- | --- |
| GET /job/recommendations/options | 获取方向、城市、预设、排序和默认筛选项 | 求职者权限；不返回演示默认城市/薪资 |
| GET /job/recommendations/context?resumeId=... | 读取所选简历默认推荐上下文 | 本人归属；允许方向缺失，提示补选 |
| POST /job/recommendations | 执行推荐分页查询 | 本人归属、可选覆盖、全局评分排序后分页 |

完整字段表与示例见`job-recommendation-api-contract.md`。没有修改数据库表、前端或原有岗位保存接口，也没有提交/推送Git。

## 3. Controller与DTO为什么这样设计

`JobRecommendationController`只承担路由、@Valid和ThreadLocal当前用户提取。请求体没有userId、企业审核状态或预置分数，用户不能伪造他人身份或修改准入条件。

`JobRecommendationQueryDTO`复用已有分页边界常量；新增默认开关与批次常量有清晰命名。金额、分页、权重只接受JSON整数，布尔只接受true/false，不把1.5截断为1，也不把字符串false强转为布尔。

`RecommendationWeightsDTO`要求完整五项、每项0～100且总和大于0。preset与weights不能同时指定。大写维度码作为显式别名，options返回的权重可以原样回传。

`RecommendationPreferencesDTO`借助FieldAwareDTO的setter记录字段存在性：未传继承简历默认，明确null只清空本次值。例如city=null使本次城市项UNKNOWN，不会删除数据库默认城市。

方向覆盖还要处理一个容易漏掉的情况：默认职位文本“后端开发”与本次FRONTEND冲突。如果直接把新方向和旧文本一起交给特征构建器，会被判为矛盾。因此本次显式选择方向时，只清空复制对象的旧职位文本，保留数据库原对象。显式清空方向也不能被旧文本重新映射回来。

JSON未知字段、非法枚举或类型沿用HTTP200/code500业务失败契约；登录失败由既有拦截器返回HTTP401。前端仍以业务code决定成功/失败，不修改既有请求拦截器。

## 4. Mapper与只读事务调用链

```text
Controller校验输入、取得当前用户
  → JobRecommendationServiceImpl捕获统一上海asOfDate
  → RecommendationSnapshotReader（独立Spring代理）
       开启只读REPEATABLE_READ事务
       → requireJobSeeker
       → WHERE resume.id=? AND user_id=? 验证本人归属
       → 读取本简历意向、教育、工作、技能的必要字段
       → 查询ACTIVE岗位 + APPROVED企业 + 两个可选排除条件
       → 分批加载STRUCTURED能力子表
       结束读取事务
  → 新对象合并本次偏好，构建特征
  → 按明确方向与可选严格城市筛选
  → 逐岗位五维评分，保留UNKNOWN与逐项证据
  → 全部候选稳定排序
  → 分页切片并构造独立VO
```

使用独立读取Bean是为了让@Transactional真正经过Spring代理，避免本类私有自调用失效。角色、简历、子表、岗位及当前用户的投递标记都来自同一个可重复读快照，避免在一次响应中拼接两个时刻的数据。

应用query标记NOT_SUPPORTED，读取器自己开启并结束事务；这样未来调用真实模型时，也不会无意被外层数据库事务包住。本阶段没有模型网络请求、写事务或缓存依赖。

`JobRecommendationMapper`显式选择推荐所需列，不读取姓名、手机号、邮箱、政治面貌、学校名称或整份简历正文。推荐岗位卡片直接关联企业名称/Logo，applied通过当前用户与岗位的EXISTS得到，避免后续逐岗位查企业或投递。

SQL不在评分前分页：否则数据库第一批低分岗位会挤掉后面的高分岗位。方向和城市需要精确规范化后判断，因此当前在应用内过滤，再进行全局排序。

结构化能力用IN批量查询，每批200个岗位，不对每个岗位单独查一次。所有STRUCTURED岗位都有显式列表，即便没有子行也是[]；空数组不能回退兼容文本。单元测试用201个结构化岗位验证恰好两次能力查询。

## 5. Service与VO拆解

`options()`返回版本化资源中真实支持的城市、明确方向、三套权重及原型两种排序；语义状态明确为未启用。

`context()`读取所选简历并构建摘要：申报阶段、确认正式月数、最高已开始学历、技能原文及默认偏好。缺少方向时仍可成功读取，以便前端让用户补选；它不默默选BACKEND、杭州或15000元。

`query()`执行资格读取、覆盖、过滤和计算。覆盖使用新JobPreference对象，不修改MyBatis读出的默认对象，更不会调用任何UPDATE Mapper。

源数据中的非法薪资进入UNKNOWN；本次输入非法数值由DTO拒绝，显式覆盖导致区间倒置由Service拒绝。二者区分了“历史脏数据可解释地读取”与“新增请求不允许写入错误意图”。

排序使用计算器的未舍入分数。MATCH同分再按publishedAt/id降序；SALARY_DESC仅比较有效非面议月薪上限，年薪、日薪、面议或异常数值置末，再按匹配顺序比较。页偏移用long计算，超大合法页码不发生int溢出。

`RecommendationApiVO`为独立公开契约，不直接返回Mapper实体或内部未舍入值。Item包含企业/岗位卡片字段、applied/expired标记、能力来源与版本、总分、覆盖率、五维解释和能力原文证据。前端展开解释无需逐卡片再查一次评分。

低于学历要求的0分仍是SCORED，权重保留；薪资缺失UNKNOWN保留分母；有效日薪NOT_APPLICABLE排除薪资权重。总分null仍可返回岗位，不冒充0或权限错误。

## 7. 面试追问与下一任务

需要能独立解释：

1. 为什么简历归属必须进入SQL，而不能只相信请求中的resumeId和userId？
2. 为什么多个SELECT要放进同一读取快照，模型调用却应在事务结束后？
3. 为什么先分页再评分无法保证全局推荐顺序？当前全量内存实现有什么规模边界？
4. 为什么当前用户的已投递不能按“这份简历”判断，已拒绝记录为何仍属于已投递？
5. 为什么null清空不能被默认值重新填回来？为什么显式方向覆盖还要处理旧职位文本？
6. 为什么NULL总分、明确0分与不可比较维度需要不同契约？

可准确表述本阶段成果：接入按指定本人简历推荐岗位的查询接口，以只读快照和批量子表读取组织数据，返回可解释五维分数及全局排序分页结果，并使用115条持久Postman用例验证权限、过滤、缺失值和只读行为。实现由助手编写、用户复查学习，不能写为本人独立完成或夸大效果指标。
