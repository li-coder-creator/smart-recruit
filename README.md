## 📖 项目简介

**Smart Recruit** 是一个基于 **Spring Boot 3** 开发的前后端分离智能招聘系统。

项目面向**求职者**与**企业**两类用户，模拟真实招聘平台的核心业务场景，目前已实现：

- 用户注册与登录
- JWT 身份认证
- 企业与岗位管理
- 结构化简历、分页列表、默认简历与完整度
- 岗位草稿、发布、暂停、恢复与结束
- 企业招聘总览、单岗位招聘进展与列表统计
- 最近投递与岗位操作记录
- 岗位投递
- 企业处理投递与状态迁移白名单
- 简历缺失时保留历史投递
- 我的投递分页筛选、状态概览与真实事件时间线
- 企业面试安排、改期、取消与求职者近期面试
- 用户角色与权限控制
- 企业审核
- Redis 缓存
- 缓存穿透处理
- 缓存击穿处理
- 缓存空值
- Redis 互斥锁
- 有限重试
- 随机 TTL
- 提交后缓存失效与延迟二次删除
- 请求链路 TraceId
- MDC 用户上下文
- 操作日志
- 全局异常处理

后端采用 **Spring Boot + MyBatis + MySQL + Redis** 技术栈，通过 RESTful API 为前端提供业务接口。

前端项目采用 **Vue 3** 开发，独立维护于前端仓库。

**当前阶段（2026-10-21）：** 简历模块前端已提交；岗位后端的生命周期、招聘统计、操作记录和历史投递可见性已实现。企业资料扩展、私有文件、工商核验与材料审核已完成后端分阶段回归及收尾集成回归；岗位与企业资料前端适配、完整业务联调待完成。推荐人才及智能匹配仍在后续规划中。

## 🏗️ 系统架构

项目采用前后端分离架构：

```text
┌─────────────────────────────┐
│         Vue 3 前端           │
│    Element Plus / Axios     │
└──────────────┬──────────────┘
               │
               │ HTTP / RESTful API
               │
┌──────────────▼──────────────┐
│        Spring Boot 3        │
│                             │
│        Controller           │
│             ↓               │
│          Service            │
│             ↓               │
│           Mapper            │
└──────────────┬──────────────┘
               │
       ┌───────┴────────┐
       ↓                ↓
   MySQL 8.0          Redis
```

后端采用经典三层架构：

```text
Controller
    ↓
Service
    ↓
Mapper
    ↓
MySQL
```

Redis 作为缓存层：

```text
客户端请求
    ↓
Controller
    ↓
Service
    ↓
查询 Redis
    │
    ├── 命中 → 直接返回
    │
    └── 未命中
          ↓
       尝试获取互斥锁
          ↓
       再次查询 Redis
          │
          ├── 已存在 → 返回缓存
          │
          └── 仍不存在
                ↓
             查询 MySQL
                ↓
             写入 Redis
                ↓
             返回结果
```

### 岗位状态与规则

| 状态码 | 枚举 | 含义 |
| --- | --- | --- |
| 0 | `ACTIVE` | 招聘中 |
| 1 | `PAUSED` | 暂停招聘 |
| 2 | `ENDED` | 已结束 |
| 3 | `DRAFT` | 草稿 |

- 草稿允许资料不完整，岗位名称仍必填；发布时由 Service 统一校验必填资料和薪资规则。
- 已有岗位仅草稿允许发布；招聘中允许暂停，暂停后允许恢复；招聘中或暂停岗位允许结束。
- 已结束岗位没有重新发布接口；只有草稿允许物理删除。
- 内容更新 DTO 不接收 `status`，状态变化使用独立业务接口。
- 企业写操作要求审核通过并验证岗位归属；企业查询限定本企业，求职者仅浏览招聘中岗位。
- `publishedAt`、`endedAt` 记录实际操作时间；旧岗位缺失的历史时间不补造。
- 岗位字段包含类别、团队、招聘人数、用工类型、办公方式、地址、职责、要求、技能、福利及计划截止日期等。
- 薪资单位使用 `MONTH` / `DAY` / `YEAR`；面议时薪资上下限为空。旧 `description` 保留用于兼容，不自动转换为新职责或要求。

### 招聘统计口径

| 字段 | 含义 |
| --- | --- |
| `applicationCount` | 投递记录总数，同一求职者投递不同岗位分别计数 |
| `pendingApplicationCount` | 当前待处理投递数，原型中的“新”；没有未读标记 |
| `currentInterviewApplicationCount` | 当前处于面试状态的投递数，用于展示面试人数 |
| `interviewApplicationCount` | 曾实际进入面试的投递数，用于计算转化率 |
| `interviewConversionRate` | 累计面试投递数 / 投递总数 × 100，保留两位小数 |

企业投递总览统计招聘中、暂停、已结束岗位，不受岗位列表筛选和分页影响；草稿不参与投递统计。
无投递时计数为 0、转化率为 `null`；存在无法核实的面试历史时，累计面试数与转化率返回 `null`，前端显示“—”。
不能用当前面试人数代替累计面试人数计算转化率，也不能根据录用或拒绝状态推断曾面试。

企业列表使用 `CompanyJobListVO` 返回三项当前计数：先分页，再针对当前页岗位 ID 执行一次聚合查询并按 ID 合并，避免逐岗位查询和关联投递导致分页总数失真。求职者列表继续使用 `JobListVO`。

实现说明：[企业分页统计](docs/company-job-list-statistics.md)、[招聘总览](docs/company-job-overview.md)、[单岗位进展](docs/job-recruitment-progress.md)、[最近投递](docs/job-recent-applications.md)、[岗位操作记录](docs/job-activities.md)。

### 投递状态迁移

| 当前状态 | 允许的目标状态 |
| --- | --- |
| 待处理（0） | 筛选中、面试、录用、拒绝 |
| 筛选中（1） | 面试、录用、拒绝 |
| 面试（2） | 录用、拒绝 |
| 录用（3） | 无，终态 |
| 拒绝（4） | 无，终态 |

同状态重复操作、回退和终态变更均拒绝。后端按白名单独立校验，前端仅展示允许的目标。
`hasInterviewed` 为 `true` / `false` / `null`，分别表示确认曾进入面试阶段、确认未进入、旧记录未知；不证明实际出席。

投递详情先查询原始记录、检查访问者和归属，再读取展示资料。简历缺失时仍返回原投递及 `resumeId`，`resumeAvailable=false`、`resumeTitle=null`；简历标题为空不表示记录缺失。此机制保留进度记录，不能恢复已经删除的简历内容。

实现说明：[投递白名单](docs/application-status-whitelist.md)、[历史投递可见性](docs/historical-application-visibility.md)。

### 我的投递与面试契约

求职者分页默认 `page=1`、`pageSize=10`、`dateRange=LAST_30_DAYS`；每页 1～100，
`status` 沿用 0～4，`keyword` 按岗位标题/企业名称字面搜索。日期范围仅接受
`LAST_7_DAYS`、`LAST_30_DAYS`、`ALL`，按 Asia/Shanghai 自然日包含今天，列表始终排除晚于本次服务器时间的记录。
概览统计本人全部历史投递的当前状态，不受列表的日期、关键词、分页影响；`interviewCount` 为当前面试阶段数量。

`historyComplete` 表示从投递创建起事件是否完整。旧记录保持 false；新投递与唯一 APPLIED 事件同事务成功后为 true。
跳阶段只记录实际起点和终点，不补造中间阶段。岗位、企业、简历展示字段取当前关联资料，尚未保存投递时完整快照。
`jobAvailable`/`companyAvailable` 表示资料存在，`resumeAvailable` 还检查简历归属；`jobViewable` 要求岗位 ACTIVE 且企业 APPROVED。

面试仅由所属的已审核企业创建、改期和取消，写操作要求投递 INTERVIEW。同一投递最多一场未取消且未结束的有效安排。
改期为完整内容替换、仅允许尚未开始的场次；手动取消允许进行中但尚未结束的场次。修改和取消携带当前整数 `version`，成功后递增。
ONLINE 必填平台和 http/https 链接，OFFLINE 必填地址，两种方式字段互斥；会议链接不会由服务端访问。

存储状态为 SCHEDULED/CANCELLED，`timingStatus` 根据统一服务器时间派生 UPCOMING/ONGOING/EXPIRED/CANCELLED。
时间过期不能据此推断出席或完成面试。近期查询也可返回正在进行的面试；无安排时 `interview=null`，仍返回 `serverTime` 和 `timeZone`。
会议链接、地址及可见说明仅向相关双方提供；事件仅返回白名单变化，不返回操作者账号、原始 detailJson 或内部取消来源。

契约与实现：[字段契约](docs/application-upgrade-field-contract.md)、[事件事务](docs/application-upgrade-phase-3.md)、
[面试排期](docs/application-upgrade-phase-4.md)、[统一验收说明](docs/application-upgrade-phase-5.md)。

# ⚡ Redis 缓存模块

项目已完成 Redis 基础缓存模块学习与实践，并针对岗位详情查询进行了缓存优化。

## 1. Cache Aside Pattern

当前采用旁路缓存策略：

```text
查询：

Redis
 ↓
命中 → 直接返回
 ↓
未命中
 ↓
MySQL
 ↓
写入 Redis
 ↓
返回
```

更新：

```text
更新 MySQL 并提交事务
 ↓
删除 Redis 缓存
```

---

## 2. 缓存空值

针对不存在的岗位：

```text
Redis
 ↓
未命中
 ↓
MySQL
 ↓
岗位不存在
 ↓
Redis 写入特殊空值
 ↓
设置较短 TTL
```

再次请求：

```text
Redis
 ↓
命中空值
 ↓
直接返回“岗位不存在”
```

用于减少不存在岗位的重复数据库查询，缓解这类**缓存穿透**。

---

## 3. 互斥锁缓解缓存击穿

多个线程同时访问同一个未缓存岗位时：

```text
A ──→ Redis 未命中 ──→ 获取锁成功
                         ↓
                       查询 MySQL
                         ↓
                       写入 Redis
                         ↓
                       释放锁

B ──→ Redis 未命中 ──→ 获取锁失败
                         ↓
                       等待重试
                         ↓
                       Redis 命中
                         ↓
                       返回

C ──→ Redis 未命中 ──→ 获取锁失败
                         ↓
                       等待重试
```

使用 Redis `SETNX` 思路实现互斥锁：

```java
redisTemplate.opsForValue()
        .setIfAbsent(lockKey, uuid, 10, TimeUnit.SECONDS);
```

使用 UUID 标识锁持有者，并通过 Lua 原子比较与删除释放锁，避免误删其他线程持有的锁。

---

## 4. 有限重试

没有获取到锁的线程不会无限等待。

当前采用有限重试机制：

```text
获取锁失败
    ↓
等待 50ms
    ↓
重新查询 Redis
    ↓
Redis 命中 → 返回
Redis 未命中 → 再次尝试
    ↓
达到最大重试次数
    ↓
返回系统繁忙
```

当前最大重试次数为 3 次。

---

## 5. 锁安全释放

为了避免锁过期后被其他线程重新获取，而原线程继续删除新锁的问题，当前使用 UUID 标识锁：

```text
线程 A
 ↓
获取 lock:job:5
 ↓
value = UUID-A

锁过期

线程 B
 ↓
获取 lock:job:5
 ↓
value = UUID-B

线程 A 执行业务结束
 ↓
检查当前锁 value
 ↓
UUID-A != UUID-B
 ↓
A 不删除锁
```

比较与删除在同一段 Lua 中执行，避免两步 Redis 操作之间的竞争窗口。锁有有效期，这个机制不代表所有长耗时和故障场景都已经得到验证。

---

## 6. 随机 TTL

为了降低大量缓存同时过期造成缓存雪崩的风险，缓存 TTL 使用：

```text
基础 TTL + Random 随机时间
```

使不同缓存的过期时间产生一定随机性，降低大量缓存同时失效的概率。

---

## 7. 事务提交后失效与延迟二次删除

当前岗位写操作在事务提交后的 `afterCommit` 回调中失效缓存；事务回滚不会执行该回调。

基本流程：

```text
更新数据库与操作记录
        ↓
提交事务
        ↓
第一次删除缓存
        ↓
调度延迟任务（当前配置 100ms）
        ↓
第二次删除缓存
```

延迟二次删除降低旧读取回填缓存的风险。数据库已经提交后，缓存删除或调度失败会记录日志，不把已提交业务伪装成回滚失败；当前没有可靠重试或版本控制，因此不承诺缓存严格一致。

---

## 8. Redis 序列化

针对 Java 对象直接存入 Redis 时的序列化问题，项目自定义了 RedisTemplate 配置。

使用：

- `StringRedisSerializer` 处理 Key
- `Jackson2JsonRedisSerializer` 处理 Value
- `ObjectMapper`
- `JavaTimeModule`

解决 `LocalDateTime` 等 Java 8 时间类型在 Redis 序列化 / 反序列化过程中的兼容问题。

---

岗位操作记录回归已覆盖预热详情缓存后暂停岗位、再次读取新状态等功能场景，见 [验收报告](docs/job-panels-regression-2026-10-04.md)。
