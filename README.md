## 📖 项目简介

**Smart Recruit** 是一个基于 **Spring Boot 3** 开发的前后端分离智能招聘系统。

项目面向**求职者**与**企业**两类用户，模拟真实招聘平台的核心业务场景，目前已实现：

- 用户注册与登录
- JWT 身份认证
- 企业与岗位管理
- 简历管理
- 岗位投递
- 企业处理投递
- 用户角色与权限控制
- 企业审核
- Redis 缓存
- 缓存穿透处理
- 缓存击穿处理
- 缓存空值
- Redis 互斥锁
- 有限重试
- 随机 TTL
- 延迟双删
- 请求链路 TraceId
- MDC 用户上下文
- 操作日志
- 全局异常处理

后端采用 **Spring Boot + MyBatis + MySQL + Redis** 技术栈，通过 RESTful API 为前端提供业务接口，并已完成核心业务模块的前后端接口联调。

前端项目采用 **Vue 3** 开发，独立维护于前端仓库。

## 🏗️ 系统架构

项目采用前后端分离架构：

```text
┌─────────────────────────────┐
│         Vue 3 前端           │
│    Element Plus / Axios     │
└──────────────┬──────────────┘
               │
               │ HTTP / RESTful API
               │
┌──────────────▼──────────────┐
│        Spring Boot 3        │
│                             │
│        Controller           │
│             ↓               │
│          Service            │
│             ↓               │
│           Mapper            │
└──────────────┬──────────────┘
               │
       ┌───────┴────────┐
       ↓                ↓
   MySQL 8.0          Redis
```

后端采用经典三层架构：

```text
Controller
    ↓
Service
    ↓
Mapper
    ↓
MySQL
```

Redis 作为缓存层：

```text
客户端请求
    ↓
Controller
    ↓
Service
    ↓
查询 Redis
    │
    ├── 命中 → 直接返回
    │
    └── 未命中
          ↓
       尝试获取互斥锁
          ↓
       再次查询 Redis
          │
          ├── 已存在 → 返回缓存
          │
          └── 仍不存在
                ↓
             查询 MySQL
                ↓
             写入 Redis
                ↓
             返回结果
```

# ⚡ Redis 缓存模块

项目已完成 Redis 基础缓存模块学习与实践，并针对岗位详情查询进行了缓存优化。

## 1. Cache Aside Pattern

当前采用旁路缓存策略：

```text
查询：

Redis
 ↓
命中 → 直接返回
 ↓
未命中
 ↓
MySQL
 ↓
写入 Redis
 ↓
返回
```

更新：

```text
更新 MySQL
 ↓
删除 Redis 缓存
```

---

## 2. 缓存空值

针对不存在的岗位：

```text
Redis
 ↓
未命中
 ↓
MySQL
 ↓
岗位不存在
 ↓
Redis 写入特殊空值
 ↓
设置较短 TTL
```

再次请求：

```text
Redis
 ↓
命中空值
 ↓
直接返回“岗位不存在”
```

用于解决**缓存穿透**问题。

---

## 3. 互斥锁解决缓存击穿

多个线程同时访问同一个未缓存岗位时：

```text
A ──→ Redis 未命中 ──→ 获取锁成功
                         ↓
                       查询 MySQL
                         ↓
                       写入 Redis
                         ↓
                       释放锁

B ──→ Redis 未命中 ──→ 获取锁失败
                         ↓
                       等待重试
                         ↓
                       Redis 命中
                         ↓
                       返回

C ──→ Redis 未命中 ──→ 获取锁失败
                         ↓
                       等待重试
```

使用 Redis `SETNX` 思路实现互斥锁：

```java
redisTemplate.opsForValue()
        .setIfAbsent(lockKey, uuid, 10, TimeUnit.SECONDS);
```

使用 UUID 标识锁持有者，避免一个线程错误删除其他线程持有的锁。

---

## 4. 有限重试

没有获取到锁的线程不会无限等待。

当前采用有限重试机制：

```text
获取锁失败
    ↓
等待 50ms
    ↓
重新查询 Redis
    ↓
Redis 命中 → 返回
Redis 未命中 → 再次尝试
    ↓
达到最大重试次数
    ↓
返回系统繁忙
```

当前最大重试次数为 3 次。

---

## 5. 锁安全释放

为了避免锁过期后被其他线程重新获取，而原线程继续删除新锁的问题，当前使用 UUID 标识锁：

```text
线程 A
 ↓
获取 lock:job:5
 ↓
value = UUID-A

锁过期

线程 B
 ↓
获取 lock:job:5
 ↓
value = UUID-B

线程 A 执行业务结束
 ↓
检查当前锁 value
 ↓
UUID-A != UUID-B
 ↓
A 不删除锁
```

从而避免误删其他线程持有的锁。

---

## 6. 随机 TTL

为了降低大量缓存同时过期造成缓存雪崩的风险，缓存 TTL 使用：

```text
基础 TTL + Random 随机时间
```

使不同缓存的过期时间产生一定随机性，降低大量缓存同时失效的概率。

---

## 7. 延迟双删

项目在缓存更新场景下的**延迟双删策略**。

基本流程：

```text
第一次删除缓存
        ↓
更新数据库
        ↓
等待一段时间
        ↓
第二次删除缓存
```

延迟双删主要用于处理并发读写场景下的缓存一致性问题。

---

## 8. Redis 序列化

针对 Java 对象直接存入 Redis 时的序列化问题，项目自定义了 RedisTemplate 配置。

使用：

- `StringRedisSerializer` 处理 Key
- `Jackson2JsonRedisSerializer` 处理 Value
- `ObjectMapper`
- `JavaTimeModule`

解决 `LocalDateTime` 等 Java 8 时间类型在 Redis 序列化 / 反序列化过程中的兼容问题。

---

## 9. Redis 并发测试

使用 JMeter 对岗位详情接口进行并发测试。

测试结果：

```text
正常岗位：

200 次并发查询
        ↓
数据库查询约 1 次
        ↓
其他请求从 Redis 获取


不存在岗位：

200 次并发查询
        ↓
数据库查询约 1 次
        ↓
其他请求从 Redis 获取空值
```

验证了：

- Redis 缓存命中
- 缓存空值
- 互斥锁
- 有限重试
- 缓存击穿处理

在当前测试场景下能够正常工作。
